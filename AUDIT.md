# GridCraft v4.0.0 — Read-only production audit

## 1. Executive summary

1. The callback exchanges the OAuth code and fetches `/user`, then **blocks session-cookie creation on successful artwork-repository setup** (`authController.handleGitHubCallback`).
2. The current 403 is therefore in `albumService.initializeExistingRepo` / `#ensureRepository`, before the cookie is set; the code logs the GitHub message but not the failing URL.
3. If the repository is absent, `POST /user/repos` is a likely failure point for this GitHub App user-token flow; its only fallback handles 422, not 403.
4. Installation and `Contents: write` access also need confirmation for `gridcraft-artworks`; the code has no installation flow.
5. After sign-in is unblocked, `/tmp` SQLite on Vercel remains ephemeral, so GridCraft collaboration data is not durable.

## 2. Auth flow trace

1. **Login click:** `src/Header.jsx` renders “Continue with GitHub” and calls `onLogin`; `src/App.jsx` passes `login` from `useAuth`. `src/hooks/useAuth.jsx:66-68` sets `window.location.href` to `apiClient.getLoginUrl()`, which returns `/api/v1/auth/github` (`src/services/apiClient.js:72-73`).
2. **OAuth initiation:** `server/src/routes/authRoutes.js:13` routes `GET /github` through `preventCaching` (`Cache-Control: no-store`) to `AuthController.startGitHubAuth` (`server/src/controllers/authController.js:45`). The controller creates random state, sets the `gc_oauth_state` HttpOnly/Lax cookie, and redirects to `GitHubAuthService.getAuthorizationUrl` (`githubAuthService.js:15`). The URL is `https://github.com/login/oauth/authorize` and includes `client_id`, `state`, and `redirect_uri=<BACKEND_URL>/api/v1/auth/github/callback`.
3. **Callback and state:** GitHub sends the browser to `GET /api/v1/auth/github/callback?code=...&state=...`; the route also disables caching (`authRoutes.js:16`). `AuthController.handleGitHubCallback` (`authController.js:63`) reads and clears the state cookie, then checks state in constant time. A mismatch or missing cookie exits before token exchange.
4. **Token exchange:** With valid state and code, `handleGitHubCallback` calls `GitHubAuthService.exchangeCodeForToken` (`authController.js:122`; `githubAuthService.js:25`). This is `POST https://github.com/login/oauth/access_token`, with client ID, client secret, code, and the same callback URI.
5. **Identity lookup:** It calls `fetchUserProfile` (`authController.js:125`; `githubAuthService.js:69`), which makes `GET https://api.github.com/user` with the access token.
6. **Repository setup — current failure boundary:** Before encrypting the token or setting any session cookie, `handleGitHubCallback` awaits `albumService.initializeExistingRepo` (`authController.js:127`). It delegates to `#ensureRepository` (`server/src/services/albumService.js:90-143`):
   - `GET /repos/{login}/gridcraft-artworks` (`#getRepository`, line 82).
   - Only if that GET returns 404: `POST /user/repos` to create the public repo (line 100). A 422 is caught and followed by another `GET /repos/{login}/gridcraft-artworks` (line 113); other statuses, including 403, propagate.
   - If the repo is private, setup stops with 409.
   - `GET /repos/{login}/gridcraft-artworks/contents/.gridcraft/catalog.json` (`#readFile`, lines 125-128, 185-192). Only a 404 triggers `PUT /repos/{login}/gridcraft-artworks/contents/.gridcraft/catalog.json` (`#writeFile`, lines 130-139, 194-207).
   - On success, the service upserts the user and default branch in SQLite (lines 141-142).
7. **Cookie and redirect:** Only after setup succeeds does the controller encrypt the token, sign the session payload, set the HttpOnly `gc_session` cookie, then redirect to `<FRONTEND_URL>/?auth_success=1` (`authController.js:130-154`). On failure it logs `[AUTH_CALLBACK_ERROR] <message>` and redirects with `auth_error` (lines 156-168). The frontend reads the error and displays `Sign in error: ...` (`src/hooks/useAuth.jsx:49-59`).

**Exact current failure step:** it is after `GET /user`, during step 6 (`initializeExistingRepo`), and before session-cookie issuance. The code alone **cannot identify which of the GitHub requests returned the 403**: `githubRequest` throws the API message (`server/src/utils/githubClient.js:80-107`), while the callback log records only `err.message` (`authController.js:156`). If the repo does not exist and the initial repo GET returned 404, `POST /user/repos` is the leading candidate; if the repo exists, the failing request may instead be the repo GET or catalog GET/PUT. Confirm the request URL/method in a controlled diagnostic or by adding safe endpoint-stage logging (never log tokens).

## 3. Root cause analysis (ranked; exact failing request needs confirmation)

1. **Repository not installed for the App / insufficient installation access — Plausible.** Code confirms callback does not start an App-installation flow: after OAuth it immediately accesses `gridcraft-artworks`. `#ensureRepository` calls the repository endpoint and later contents endpoints with the user access token (`albumService.js:90-143`); no installation token is created (the configured App ID/private key are not used in this path). Whether this token has access depends on the App’s installation and granted repository permissions. **Check:** GitHub **Settings → Developer settings → GitHub Apps → gridcraft-auth → Install App** (or the user/organization’s Installed GitHub Apps page); confirm it is installed on the account that owns `gridcraft-artworks`, that repository is selected, and the installation has Contents read/write. If the App is meant to authorize during installation, confirm the owner actually completed that installation/authorization.
2. **`POST /user/repos` with this token — Plausible; high-priority candidate when the repo is absent.** `#ensureRepository` attempts this endpoint only after a 404, catches only 422, and does not provide another creation mechanism (`albumService.js:90-116`). A 403 therefore aborts `initializeExistingRepo`, and the callback cannot set a session. Whether GitHub supports this endpoint for this App’s user access token and which permission it requires must be checked against the GitHub REST documentation for **Create a repository for the authenticated user** and the App’s authorization type. **Check:** establish whether the user already has `gridcraft-artworks`; if not, identify the exact 403 request in function diagnostics and verify GitHub’s supported token types/permissions for `POST /user/repos`. Do not assume adding `Administration` resolves an unsupported token type.
3. **Catalog write permission — Plausible if the failure is the catalog PUT.** `#ensureRepository` writes `.gridcraft/catalog.json` if its GET returns 404; this requires Contents write. `docs/GITHUB_APP_SETUP.md:24-29` does list `Contents: Read & Write`, but that documentation does not prove the live installation was granted the current permission. **Check:** GitHub App → **Permissions & events**, then its installation’s configured repository access; confirm Contents is Read and write for `gridcraft-artworks`, and approve any pending permission update. `Administration: Read & Write` in that document is not used by any App-authenticated repository-creation code; the implementation calls `POST /user/repos` as a user token. It is unnecessary for ordinary file access and is broad. Whether it is needed for that creation endpoint is **needs confirmation** from the endpoint’s supported-auth documentation; do not grant it as a speculative fix.
4. **Login is coupled to library setup — Confirmed by code (design/root-cause amplifier).** `handleGitHubCallback` awaits `initializeExistingRepo` before encrypting/signing the session and setting the cookie (`authController.js:122-147`). Thus a missing app installation, unsupported repository creation, 403 on a file permission, or any transient GitHub error becomes a complete sign-in failure. **Check:** no GitHub setting can make this coupling safe; confirm by observing that the callback error occurs before `Set-Cookie`. Separate authentication/session establishment from optional repository setup.
5. **Wrong/mismatched client credentials or token expiration — Plausible, lower likelihood for this exact 403.** `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` are used for OAuth authorization and code exchange (`githubAuthService.js:15-52`). A mismatch more commonly fails at authorize/token exchange, before repository setup, so it is less consistent with a GitHub 403 `Resource not accessible by integration`. `exchangeCodeForToken` returns `expiresIn` and `refreshToken`, but the callback ignores them and makes a seven-day session (`authController.js:122-147`); an expiring GitHub token can later fail API calls. **Check:** in GitHub App settings compare the configured Client ID with the Vercel `GITHUB_CLIENT_ID`, rotate/verify the secret without exposing it, and inspect the App’s user-token expiration setting. Verify callback token response metadata in a safe, non-secret diagnostic and confirm refresh handling if token expiration is enabled.

## 4. Vercel/serverless risks

- **Import-time SQLite and filesystem:** `server/src/services/appStore.js:1-4,96-100,606` imports `mkdirSync` and `node:sqlite`, opens the database in the `AppStore` constructor, and exports `new AppStore()` at module import. This happens when `api/index.js` imports `createApp()`. `config.database.path` (`server/src/config/env.js:15-18`) selects `/tmp/gridcraft.sqlite` whenever `VERCEL` is set; `/tmp` is the writable temporary area, so the project bundle’s read-only filesystem is not by itself expected to crash this function. There is **no durable-storage fallback** if `/tmp` is unavailable or DB initialization fails; cold starts/isolates also do not share durable state.
- **Node runtime:** `package.json:28-30` declares `"node": "24.x"`, which satisfies the stated `node:sqlite` runtime requirement. `vercel.json` has no runtime/Node setting; confirm the deployed project’s Node.js version is 24.x in Vercel Project Settings. If the configured runtime is older, importing `node:sqlite` can fail before the handler starts.
- **Ephemeral data:** The SQLite schema (`appStore.js:8-90`) persists users, album index, issues, issue comments/labels/assignees, pull requests, pull comments/reviews, and pull file snapshots. Under Vercel `/tmp`, these are best-effort per warm instance and can disappear or diverge across instances. GitHub’s repository files (album/story/artwork JSON, catalog, commits, branches) remain durable in GitHub. The album index can be reconstructed for a user by `AlbumService.listAlbums` syncing manifests, but GridCraft-created issues/PRs/comments/reviews and their snapshots cannot be reconstructed from GitHub.
- **Routing/export:** `vercel.json:2-10` routes `/api/(.*)` to `/api` before the catch-all `/(.*)` to `/index.html`. `api/index.js:1-3` default-exports `createApp()` and does not call `app.listen`; `server/src/server.js:7` calls `listen` only for local development. The entry and rewrite are present; confirm the deployed Vercel function maps the rewrite as expected.
- **Cookies/proxy/environment:** `createApp` sets `trust proxy` to 1 (`server/src/app.js:42`). `AuthController` sets cookies `HttpOnly`, `SameSite=Lax`, `Secure=config.isProduction` (`authController.js:7-14`); `isProduction` is true for `NODE_ENV=production` or `VERCEL_ENV=production` (`env.js:9-10`). This should support same-origin HTTPS Vercel OAuth; verify Vercel’s production environment is set and test that the browser sends `gc_oauth_state` on the top-level callback. Both URLs should be the one project origin; defaults otherwise point to localhost.
- **Caching:** `/auth/github` and `/auth/github/callback` set `Cache-Control: no-store` (`server/src/routes/authRoutes.js:7-16`); `/auth/me`, `/auth/logout`, and `/auth/disconnect` do not explicitly set it (lines 19-25). Add no-store to all auth/session responses to avoid intermediary/browser caching of user-specific state.
- **CORS:** `app.js:69-84` permits `config.frontendUrl` plus two localhost origins, with credentials. Same-origin production needs no CORS; if frontend and backend origins differ, `FRONTEND_URL` must exactly equal the browser Origin (scheme/host/port, no path or trailing slash). Unlisted preview/custom domains are rejected by CORS.
- **Fallback secrets — High security risk:** `env.js:30-31` substitutes fixed development `SESSION_SECRET` and `TOKEN_ENCRYPTION_KEY` values and does not reject them when `isProduction` is true. Production missing either secret uses a publicly visible fallback: signed sessions can be forged and encrypted GitHub tokens are recoverable with the fallback key. Set strong independent production secrets and add startup validation that refuses those defaults.
- **Request size:** `app.js:88` limits JSON to 2 MB, below Vercel’s approximately 4.5 MB function request-body ceiling. The 128×128 artwork schema allows 16,384 cells with at most 9-character hex color values (`server/src/validators/artworkValidator.js:4-8,55-67`), roughly under 0.2 MB for the cells plus JSON overhead; the supported artwork payload itself should fit. Oversized requests receive the app’s 413 response (`errorHandler.js:20-41`).
- **Duration / sequential GitHub calls:** No function `maxDuration` is declared in `vercel.json`; actual limit depends on Vercel project plan/runtime and **needs confirmation** in Project Settings. `listAlbums` → `#syncUserAlbums` reads each `album.json` sequentially (`albumService.js:145-166`), so one list request costs one manifest GET per album in addition to repository/tree calls. Fork reads each source blob and writes each copied file sequentially (`albumService.js:314-353`); delete reads and deletes each file sequentially (`albumService.js:494-505`); pull merge fetches/creates blobs serially per changed file (`pullRequestService.js:259-290`). These can exceed a constrained function duration as album/file counts grow. `githubRequest` retries GETs up to three times and honors `Retry-After` (`githubClient.js:40-75`), which can further extend duration. Check function duration logs for real workload before setting limits or parallelizing writes.

## 6. GitHub App configuration checklist

- **Callback URL:** register exactly `https://gridcraft-by-me.vercel.app/api/v1/auth/github/callback` in `gridcraft-auth`. Keep the local callback too only if supported/configured for local development. It must match the `redirect_uri` generated from `BACKEND_URL` exactly.
- **OAuth flow:** enable **Request user authorization (OAuth) during installation** if the intended App setup requires it, but note that checking this option does not install the App on a user’s repo. Current frontend links directly to `/login/oauth/authorize`; it has no App-install URL or installation callback.
- **Installation:** confirm the App is installed on the account owning `gridcraft-artworks`, and the repository is selected. If users are expected to create that repo, clarify how installation happens before repo setup.
- **Repository permissions:** `Contents: Read & Write` is needed for catalog/manifests/artwork writes; `Metadata: Read` is required. Ensure the installation has accepted those exact permissions.
- **Administration:** the setup guide lists `Administration: Read & Write` to create the repo (`docs/GITHUB_APP_SETUP.md:24-29`). That is broad and is not required for normal Contents API work. The current code does not use App credentials to create a repo; it attempts `POST /user/repos` with the user token (`albumService.js:100-110`). Verify that endpoint’s currently supported token types and permission requirements before enabling Administration; it may not fix an unsupported endpoint/token combination.
- **Account permissions:** the guide’s “Email addresses” is marked optional and the code only calls `GET /user`; it does not call `/user/emails`. No email permission is required by current code. “User Profile” is not a repository permission and basic `/user` profile retrieval is part of the OAuth identity call.
- **Token expiration:** inspect the App’s user authorization token-expiration setting. The server stores access token but ignores `expiresIn` and `refreshToken`; if expiration is enabled, sessions can outlive the access token. Either implement refresh-token handling or align application session behavior with the App’s expiry policy.

## 8. Recommended fix plan

1. **Decouple sign-in from library initialization (first PR).** Files: `server/src/controllers/authController.js`, `server/tests/auth.test.mjs`. After validated OAuth identity, issue the encrypted/signed session cookie and redirect even if optional repo setup fails; report setup status separately without losing auth. Risk: low-to-medium; make sure setup failure is not misrepresented as a ready library.
2. **Show a setup banner when the repo or App installation is missing.** Files: `src/hooks/useAuth.jsx`, `src/components/DashboardShell.jsx`, API/controller response as needed. Present a recoverable, actionable “install/authorize App” or “create/select library” state instead of failing sign-in or a generic empty dashboard. Risk: medium; define states for absent repo, missing installation, private repo, and permission denial.
3. **Instrument GitHub operation stage and repair repo provisioning.** Files: `server/src/services/albumService.js`, `server/src/utils/githubClient.js`, targeted tests. Log safe method/path and stage for failures; never include bearer token, code, or client secret. Confirm supported GitHub auth for `POST /user/repos`; if unsupported, use an explicit App installation/create flow or require a pre-created repo. Catch only documented recoverable statuses and make the UI explain other failures. Risk: medium; GitHub setup behavior changes.
4. **Verify GitHub App settings and production env as a single deployment configuration change.** Files: `docs/GITHUB_APP_SETUP.md`, optionally `.env.example`. Register the exact production callback, confirm installation/repository selection and Contents permission, set matching `FRONTEND_URL`/`BACKEND_URL`, and validate the deployed Client ID/secret pairing. Risk: low; incorrect callback or env values continue to block OAuth.
5. **Reject fallback secrets in production and cover session expiry.** Files: `server/src/config/env.js`, `server/tests/auth.test.mjs` (and config tests if added). Require strong distinct secrets; implement token refresh if App expiry is enabled or handle expiry with a fresh sign-in. Risk: medium; production deploy must populate secrets before rollout.
6. **Move SQLite data to durable shared storage.** Files: `server/src/config/env.js`, `server/src/services/appStore.js`, persistence/service tests, deployment configuration. Replace `/tmp` SQLite with a durable database appropriate for serverless concurrency; retain GitHub as durable artwork storage. Risk: high; schema/data migration and concurrent-write semantics need a migration plan.
7. **Bound GitHub-heavy operations and harden auth caching.** Files: `server/src/services/albumService.js`, `server/src/services/pullRequestService.js`, `server/src/routes/authRoutes.js`, tests and Vercel function configuration. Measure function durations, paginate/bound or safely parallelize read work, keep writes ordered, set appropriate function duration, and add no-store to all auth responses. Risk: medium; GitHub rate limits and partial-write behavior must remain correct.
8. **Align album listing semantics and docs.** Files: `server/src/services/albumService.js`, `server/src/services/appStore.js` or `src/components/DashboardShell.jsx`, `docs/API.md`, `docs/GITHUB_APP_SETUP.md`. Either scope list to the authenticated user or explicitly call it public discovery; clarify unused permissions/env values. Risk: low-to-medium; API/UI expectations may change.

## 9. Verification steps after deployment

1. `GET https://gridcraft-by-me.vercel.app/api/v1/health` should return JSON with `status: "ok"`, version `4.0.0`, and `githubApp: "gridcraft-auth"`. A 404/HTML response means the Vercel API rewrite/function is not serving the Express app; a function startup error points to runtime/import/SQLite setup.
2. `GET https://gridcraft-by-me.vercel.app/api/v1/auth/github?format=json` should return `{ "url": "...", "state": "..." }`. Parse the `url` and confirm its `redirect_uri` query parameter is exactly `https://gridcraft-by-me.vercel.app/api/v1/auth/github/callback`; confirm the response includes a `gc_oauth_state` Set-Cookie with `HttpOnly`, `SameSite=Lax`, and `Secure` in production.
3. Complete the real browser flow (the cookie must be carried through GitHub’s top-level callback). In Vercel **Functions → Logs**, expect request logs for `/api/v1/auth/github` and `/api/v1/auth/github/callback`. Do not share token/code/state values from logs.
4. If callback fails, inspect `[AUTH_CALLBACK_ERROR]` and the error message. A 403 `Resource not accessible by integration` confirms failure before session creation, but **current logging does not show which GitHub endpoint**. Add the safe method/path diagnostic from fix 3 or reproduce against an endpoint-stage test to distinguish repo GET, `POST /user/repos`, catalog GET, and catalog PUT.
5. Interpret the identified endpoint:
   - `GET /repos/{login}/gridcraft-artworks` 403: verify App installation/repository visibility/permissions; 404 instead means code will try creation.
   - `POST /user/repos` 403: confirm endpoint supports this GitHub App user token; create/install the repo through a supported flow if not.
   - Catalog contents GET/PUT 403: verify the App installation has Contents read/write on that exact repository.
   - OAuth token exchange or `GET /user` failure: verify Client ID/secret pair, callback registration, and authorization grant before investigating repository permissions.
6. After callback reports success, confirm a `gc_session` Set-Cookie and then `GET /api/v1/auth/me` returns `authenticated: true`. If redirect says success but `/me` is unauthenticated, check cookie domain/path/Secure handling, state/session secret consistency, and production environment settings.
7. A successful sign-in with a missing library should show the planned setup banner, not block identity/session. Verify that creating the repo/catalog and subsequent album file operations succeed.
8. For persistence acceptance, create an issue/comment and pull request/review, then verify records survive a cold start and a second function instance. With current `/tmp` SQLite this is **not guaranteed**; passing this check requires the durable-storage change.
